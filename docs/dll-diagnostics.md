# Diagnostic-only DLL resolution (S3.1)

Dry-run inspects only the explicitly supplied PE. It queries the compiled shim registry for coverage, without invoking shims, loading host DLLs, discovering neighboring modules, allocating executable thunks or writing callable addresses to IAT slots. Mapped bytes remain read/write, not executable. Unknown symbols are reported as UNIMPLEMENTED and produce exit code 3; malformed input produces exit code 1. --game-dir is accepted for CLI compatibility but ignored. This intentionally changes native/bundled coverage reporting. It is not a sandbox and does not establish game compatibility.

DLL basenames are normalized using ASCII only; path syntax, device names, invalid extensions and ambiguous names are rejected. The portable policy test uses a fake registry. Windows CI runs the diagnostic executable on an independently generated data-only PE with an invalid neighboring DLL, confirming it is not recursively mapped. This does not prove all native DLL activity is absent (process startup and OS dependencies are separate). Future native resolution must have a separately reviewed trust policy. Module lifetime, aggregate limits and executable memory in dormant shim code remain follow-up work. Host execution HOLD.

Review hardening: the diagnostic executable links only main.cpp and pe_loader.cpp in both CMake and direct MSVC paths. A shared name manifest supplies a boolean registry, with callable shim implementations retained in source but excluded from the diagnostic target. Registered does not imply ABI correctness. CLI rejects unknown/duplicate options and missing values; use `--` before a filename beginning with `-`. The first-look wrapper rebuilds before invocation and treats exit 3 as incomplete coverage rather than success for execution. Windows tests cover registered names, known native exports remaining unresolved, valid/invalid neighboring files, malformed images, reserved basenames and CLI exit codes. This is behavioral coverage, not comprehensive OS module tracing or a guarantee about build-tool dependencies.

Closeout validation: `build_runtime.ps1 -DirectMsvc` explicitly builds the diagnostic executable only and removes an existing output before compilation; unsupported cmd metacharacters/non-ASCII build paths are rejected. `first_look.ps1` rebuilds through this mode, writes hash.txt and dryrun.txt and propagates exit 0/3 (validation/build failures exit 1). The legacy --game-dir parameter is accepted but ignored. The wrapper no longer invokes the separate Python pe_inspect tool or generates its JSON/Markdown/shim-todo reports; that tool is not approved as a substitute for the hardened diagnostic route. Windows CI exercises the direct build, existing integration suite and actual wrapper on independently generated fixtures. This is not a general audit of build-tool provenance, filesystem reparse points or legacy inspection tools (S4/S5).
