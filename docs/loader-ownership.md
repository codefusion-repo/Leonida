# Diagnostic loader ownership (S3.2)

Each Loader owns at most one Module via unique_ptr. A local candidate owns its native allocation via a noexcept VirtualFree deleter; publication happens only after validation, diagnostics, mapping and relocation succeed. Failed calls leave the loader empty; subsequent calls after success are rejected without reading a second file. No basename cache, executable memory, IAT writes or native DLL resolution. Exports are RVA values, not callable pointers. Module views are borrowed and expire with the Loader; not thread-safe.

Default policy: 256 MiB input, 512 MiB mapped image, 768 MiB combined. Checked before file allocation and before mapping; existing PE and parser-specific limits remain applicable. These are conservative diagnostic policy limits, not a total process RSS guarantee: metadata, allocator overhead, file system and concurrent Loader instances remain outside the combined accounting. No real-game compatibility established.

Portable budget tests under ASan/UBSan and Windows data-only lifecycle tests cover rollback/retry, duplicate rejection, resource limits, non-executable page protection and release on destruction. The dedicated Windows lifecycle test target additionally defines LEONIDA_LOADER_FAULT_TEST, which is absent from both production build paths. It injects exceptions at five boundaries after successful allocation (allocated, copied, relocated, protection failure, sealed), eight repetitions each, including std::bad_alloc. See memory-policy.md for S3.3 details. VirtualQuery checks the entire allocation range after each failure, and retry must succeed. It also tests preferred-base collision ownership. Broader OS tracing remains review work. Host execution HOLD.

The Module destructor is private (only its owning deleter may destroy it); the public reference is borrowed and does not transfer ownership. Loader configuration is immutable and may only lower the default nonzero caps, not raise them. The combined budget excludes parser metadata and concurrent instances. Fault probes are test-target-only, not controlled by image input, CLI or environment. They test exception unwinding, not recovery from hardware faults, process termination or a failing VirtualFree call.
