# Diagnostic memory policy (S3.3)

No executable image mappings are supported. The diagnostic loader allocates private PAGE_READWRITE pages, copies and relocates validated bytes, then seals the entire image PAGE_READONLY before publishing its borrowed Module. The full range is independently checked with VirtualQuery for committed private pages, expected permissions and allocation ownership. A protection or verification error unwinds the local RAII candidate. PE executable-section flags do not grant native execute permissions. Unknown callable shim lookups return nullptr; the unused machine-code thunk generator and its RWX pool are removed. Callable shims remain excluded from diagnostic builds.

The standalone CLI enables and reads back Windows ProcessDynamicCodePolicy before reading any image, requiring ProhibitDynamicCode and rejecting thread opt-out or remote downgrade. Failure prevents inspection. This is an additional defense, not a sandbox, and applies after process startup; already loaded modules and ordinary executable image mappings are outside this mitigation. The Loader library itself does not modify process-wide policy. Any future execution mode must be separately designed and reviewed.

Windows tests inspect every mapped region before injected faults and after sealing, including a zero-filled section with executable PE flags. Forty fault iterations cover five stages. In eight protection-failure cases the test-only target decommits its own last page and calls the real VirtualProtect; the test requires an actual nonzero Win32 error and full release of the reservation. The separate registry test never invokes a function. CLI integration checks the mitigation confirmation for valid diagnostics. The source policy guard checks named executable permissions, explicit native memory API call sites and dynamic loader locations, with negative self-tests; it is not a compiler-level or process-wide proof.

Residual scope: the excluded D3D12 shim loads a System32 DLL; optional Vulkan tools load drivers and must be reviewed separately, including DLL search and GPU/compiler behavior. CRT/OS startup imports, arbitrary third-party dependencies, build tooling and process-wide module tracing remain S4/S5/G4 work. No image code execution, no new execution mode. Host execution HOLD.
